# 用户主导的算法竞赛出题流程

## 角色与入口

用户提供题目大意、主要规则及大致思路；AI 先查重，再审查解法，通过后完成题面、程序、数据和验证。用户已有指示和已作出的决定持续有效，不重复索取同一决定。

### 用户输入文件

每道题使用题目目录下的 BRIEF.md 保存用户输入，例如 example/BRIEF.md。该文件由用户填写和维护，内容可以简略，未确定的部分写“待定”，不要求先写正式题面或完整证明。

推荐字段：题目全名、文件名标签 [id]、赛制与题型、题目大意、简要解法、预期复杂度、已知约束、目标难度或考点、部分分意图、希望保留的设计、疑问及参考来源。新题可用 `python3 new_problem.py arena --title "题目全名" --style CNOI-style` 创建目录并复制模板。全名用于标题，[id] 用于源程序与输入输出文件名，不要求全局唯一。目录名默认采用 [id]；同名目录已存在时脚本采用 arena-2 等容器名，BRIEF 中的标签仍为 arena，也可用 `--directory` 指定其他目录。赛制须在定稿前明确；部分分可以由用户给出目标，也可以由用户授权模型提出具体方案后再决定。

AI 开始时必须读取 BRIEF.md，但不得擅自改写用户的原始构思。解法分析与修改建议放入 reports/，进度和用户决定放入 STATUS.md；正式题面和题解是后续产物。仅在用户明确要求整理或更新 BRIEF.md 时修改它。

用户本次消息明确更新了设计时，以该更新为准，并在 STATUS.md 中记录与 BRIEF.md 的差异。如果不同文件或消息存在无法判断的冲突，先澄清影响当前工作的部分，不自行覆盖原始输入。

BRIEF.md 缺失或仅含模板占位符时，检查用户消息是否已提供实质输入；没有则请求补充。不得根据目录名编造题意，也不得把模板当成已确认的约束。用户修改 BRIEF.md 后，重新评估受影响的查重和解法结论。

开始时检查已有文件，简述对题意和用户解法的理解，并识别会影响判断的缺失信息。可先采用明确记录的假设进行分析；会影响最终正确性和数据范围的缺失信息须在定稿前解决。

只根据用户的授权推进：如果用户只要求查重或解释替代解法，做到该范围即可。如果用户授权完整制作，审查未发现需要用户决定的问题时直接继续。

## 第一阶段：保密查重

### 外发边界

未公开的题意、解法、代码和数据均为保密内容。联网查询会向外部服务发送查询内容，通用关键词也不能提供绝对保密保证；不得宣称已保证不泄露。

默认仅使用通用算法名、已公开问题名、宽泛模型和常见复杂度关键词查询。例如“树 路径 异或 算法”，而非复述本题特有操作、限制和目标。

不得向搜索引擎、网站、远程查重工具或其他外部服务发送：

- 完整题意或可辨识的题面片段，包括翻译和改写版本。
- 特有规则、精确约束组合、故事、标题、样例及答案。
- 核心未公开性质、证明、标程、生成器和测试数据。
- 通过多个查询拆分、累积复原上述内容的信息。

若通用查询不足以有效查重，报告覆盖局限。确实需要更具体查询时，先展示拟发送的确切文本及其泄露风险，等待用户批准后再发送。用户要求完全不外发时，仅检查本地材料或用户提供的资料。

### 比较方法与产物

先用抽象关键词查找公开候选题，阅读候选题的原始题面或可靠来源，然后在本地与本题比较。不要把本题内容提交给候选网站。

在 reports/duplicate-check.md 中记录：

- 实际查询文本、查询日期、来源链接与覆盖范围。
- 候选题的模型、操作、目标、约束与核心解法。
- 判断属于同题、关键变形、共享模型或仅共享算法，以及判断依据。
- 未覆盖的信息与不确定性。

区分“发现明确重复”“存在相似候选”“本次检索未发现明确重复”。不得把最后一项写成“原创已确认”。缺少原始题面时，不得仅凭标题或摘要确定同题。

发现明确重复或高度相似的核心设计时，先汇报证据，等待用户决定继续、修改或放弃；仅共享常见算法不自动触发暂停。

## 第二阶段：审查用户解法与替代解法

先检查用户解法的正确性、复杂度和适用前提，再分析可能的更优方法。重点包括：

- 是否可用更低时间或空间复杂度解决。
- 是否存在明显更简单、显著降低预期难度的做法。
- 是否能绕过预期考点，或利用约束直接解决。
- 是否有未覆盖的反例、隐藏前提、数值范围问题。

在 reports/solution-review.md 中记录用户思路、证明、替代方法和比较。将“猜测”“已有证明”“经程序验证”分别标明。

发现更好的可行做法时，必须先向用户报告：

1. 改进的具体方面及其对出题意图的影响。
2. 核心观察与算法步骤，用用户能理解的语言说明。
3. 正确性依据和时间、空间复杂度。
4. 一个帮助理解的小例子，必要时补充对比程序。
5. 继续使用原题、接受新解法或修改设计的可选方向。

此时将状态标记为“等待用户决定”。不要自行继续生产正式题面、完整数据或发布包；可以继续推导、验证和解释该方法，以支持用户判断。用户后续提问通常是在理解方法，不等于同意继续。

发现用户解法不成立或存在影响题目成立性的歧义时，同样先汇报反例或问题，等待设计决定。只有未证实的改进猜测时，先在本地验证；无法验证则明确不确定性，不强行下结论。

没有发现上述问题，或用户已经决定继续时，进入制作阶段。不得声称已经穷尽所有可能算法。

## 第三阶段：题目制作

按实际题型建立所需文件，沿用已有组织方式，不为了目录形式制造无用产物。

### 解法与题面

- 写出正确性证明，实现预期标程及独立思路的小规模暴力。
- 执行可行范围内的穷举或随机对拍，保存失败输入、种子及复现命令，尽量缩小反例。
- 确定输入范围、输出规则、无解和并列处理、样例，以及适用的子任务。
- 收集替代解法、部分分解法和常见错误解法。
- 后续若新发现更好的做法，仍返回第二阶段的用户决定环节。

### 赛制、题型与评分

以下为本项目的用户约定，不作为所有官方比赛的统一规则。赛制使用 `CNOI-style`、`IOI-style`、`ICPC-style` 三个名称；题型分为普通非交互题、交互题、通信题。

- **CNOI-style 非交互题**：必须采用 10、20 或 25 个正式评分数据点；数据点等分、独立评分，不绑定 Subtask。满分 100 时分别为每点 10、5、4 分。样例不计入正式评分数据点。可以将相同约束的数据点归并成一行约束表，归并不改变独立评分。
- **CNOI-style 传统题的文件约定**：一般从 `[id].in` 读入，输出到 `[id].out`，源程序基名为 [id]，如 arena.cpp。题面输入节明确“从文件 arena.in 中读入数据”，输出节明确“输出到文件 arena.out 中”。标程应对应打开文件；生成器、答案生成、checker 接口和本地验证运行目录也须匹配，不能仅在题面改文字。只有 BRIEF 或目标比赛明确采用标准输入输出时才改用该方式。IOI-style、ICPC-style 普通题默认标准输入输出，交互/通信题按接口约定。
- **CNOI-style 交互题**：类似 IOI-style，可以绑定测试包；得分必须取整。题面与 checker 必须明确取整方式，一般优先提出向下取整方案，由用户确认。一般提供第一个约束较弱、只给离散分数而无连续得分的测试包。其他测试包可以按开销评分。
- **CNOI-style** 不设置通信题。
- **IOI-style**：建议绑定 Subtask，同一个 Subtask 共用一套约束。离散评分时，须通过其中全部数据点才能获得整个 Subtask 的分数；分值无需等分，也无需为 4 或 5 的倍数。
- **IOI-style 交互、通信题**：建议根据正确做法的开销 x（操作次数、通信比特数等）用合理的连续函数 f(x) 评分。明确正确性要求、函数定义域、边界、单调性、满分/零分条件、数值精度及多数据点聚合方式。若绑定 Subtask，未通过包内正确性检查不能获得该包分数；通过后的效率得分按已公布的规则计算。不要将连续评分误写为一律只有整包满分或零分。
- **ICPC-style**：不设计部分分、评分点或 Subtask 表；题面不提“没有部分分”“不设部分分”。测试文件数量不受 CNOI 的 10/20/25 限制。

用户指定部分分目标时按目标制作；用户授权模型设计时，将约束、分值、点数/包数、对应做法与评分函数写入 `reports/`，先交由用户决定再定稿。不能根据尚未确认的评分方案声称制作完成。

数据范围表中，`n`、`m` 等变量的数值范围分别单独成列，列标题使用变量名；结构、排列或其他特殊性质另列“特殊性质”，不能把数值范围笼统合并到“附加约束”中。全局限制与表格一致，各档无特殊性质时写“无”。

数据范围表、样例限制说明等位置的测试点编号统一简写：连续两个编号用逗号分隔，如 `1, 2`；连续三个及以上用 `~` 表示区间，如 `3 ~ 6`、`7 ~ 14`。非连续编号或多个连续段以逗号分隔，如 `1, 2, 5 ~ 8, 10`。不得把缺失的编号并入区间。Markdown、Typst 和 PDF 保持一致。

### Typst 题面与 PDF

- 每题维护 `statement.md`、`statement.typ`、`statement.pdf`，同步题意、范围、样例和评分规则。
- 编写、修改 Typst 必须使用 `typst` skill；所有题面导入根目录 `problem-theme.typ`，字号、字体、页边距、页眉页码、样例框与评分表样式集中维护。
- 用 `python3 scripts/build_statement.py <题目目录>` 编译 PDF，或按 `docs/problem-theme.md` 使用 Typst CLI。无须第三方 Typst 包或远程编译服务；未公开题面不得上传外部服务。
- CNOI 正文每段（包括标题后的第一段）统一首行缩进 2em；标题、元信息、歌词、样例框、下载文件说明、表格和页眉页脚不缩进，局部规则在共用主题中限定作用范围，避免继承正文缩进。
- 编译后检查中文字体、公式、样例完整性、长行溢出、分页和标题孤行；记录编译器版本与检查结果。交付包含 Typst 源码和 PDF；交付源码内联共用主题与元信息，不额外打包根目录基础设施，保证解包后只需相同字体即可编译。

### CNOI-style 样例与下载文件

- 检验题意的小样例之外，还须提供覆盖每一档数据限制（含特殊性质组合）的下载样例；允许一组覆盖多项限制，但不能把所有档位都用同一个过小输入替代。应在允许范围内尽可能帮助选手验证正确性，覆盖边界、不同合法结构及有代表性的规模。
- 尽量额外提供一组有一定强度、规模较小、适合手工跟踪与调试的样例。它可以同时覆盖最低档限制，但作用不应仅是重复最简单的题意例子。
- `down/` 即下发文件包，也就是题面所称的“选手目录”。所有样例（题面展示的小样例和文件中的大样例）统一存放在题目目录 `down/`，顺次从 1 连续编号，不与正式评分点混合。文件名沿用标签，例如 `down/example1.in`、`down/example1.ans`，之后为 `example2.in`、`example2.ans` 等；标签来自 BRIEF，不能用容器目录名代替。
- 小样例在 Markdown、Typst、PDF 中直接展示输入输出，可配题意解释。大样例只写“见选手目录下的 `exampleN.in` 与 `exampleN.ans`。该样例满足测试点……的约束条件。”这些文件名相对于选手目录，不再重复添加 `down/` 前缀。约束有包含关系时，标注该输入实际满足的最紧一档，不罗列更宽档位；存在不可比较的限制时，只列实际满足的最具体约束组合，不声称存在唯一最紧档。
- 生成下载样例时，不得通过样例说明、特殊标号排列、可辨识的构造或共享正式点固定种子，提示预期算法、关键性质或正式数据的特殊生成规则。优先使用独立种子和题面允许的普通输入结构；必要的结构限制本身可以展示，但不得另行给出解法提示。生成与筛选细节保存在私有制作报告，不能放入选手可见的 `down/` 或样例说明。
- “有强度”主要指正确性覆盖，不要求公开样例承担卡复杂度或逼迫满分算法的任务。检查典型错解是否能在样例中得到反例，同时审查是否暴露设计意图；不能为了区分复杂度而公开正式点的针对性构造。性能分离仍由正式评分数据完成。
- 对全部样例执行输入验证、答案校验及可行的独立对拍。核对连续编号、题面数字、路径、最紧约束标注和 ZIP 内容一致；样例不计入正式评分点。按题型验证交互/通信样例接口，不强行使用普通题的输入答案文件接口。
- 上述大样例说明参考 [NOIP 2025 官方资料页](https://www.noi.cn/zxzy/lnzl/jszl/2025-12-15/854083.shtml)中的题面风格，以及可检视的[糖果店原始题面](https://qoj.ac/download.php?id=15457&type=statement)。这里只借鉴文件引用与最紧约束标注的格式；`down/` 组织、各档覆盖和手调样例是本项目约定，不表述为官方比赛的全部强制规则。

交互题下发的公开接口头文件、示例 grader 和编译说明属于样例配套文件，放在 `down/`。打包使用重复的 `--participant-file` 参数显式列出，只允许样例目录内的 `.h/.hpp/.cpp/.md` 文件；私有 grader、生成器、正式评测种子和制作报告不得下发。

旧题已有的 `samples/` 可暂由打包脚本兼容；落实本规则时须将整套样例迁移到 `down/`，同步题面与验证工具。不能留下两套含义不同或编号不一致的样例来源。

### 数据与判题

- 先制定覆盖目标，再生成边界、结构、随机、针对性和压力数据。
- 记录每个测试组的目的、参数、固定种子及针对的错误解法。
- 实现输入 validator；多解或浮点题实现适用的 checker，并检查正确、错误及非法输出的处理。
- 跑通生成、输入验证、标程求解、答案检查和候选解法回归链路。
- 验证错误解法被击败，部分分符合预期，性能测量可复现。
- 根据测量环境设置有合理余量的时空限制；无法访问正式评测环境时明确记录局限。

### 正式题解 skill

当前配置：`plain-oi-editorials`（本地 skill 名称）。

在生成或实质改写正式题解前，读取该 skill 的 `SKILL.md`，并遵循其中与当前任务相关的要求。该 skill 同样适用于用户要求的题解改写、解释和算法可视化；局部问题按 skill 的任务范围处理，不自动扩展为完整题解。

如果 skill 未安装或不可读取，记录“正式题解等待 skill 恢复”，向用户说明缺失项，继续其他不依赖它的已授权工作。可以提供用户要求的临时解法解释、算法证明和审查报告，但这些不得冒充正式题解。

该 skill 负责题解分析与表达；算法正确性仍须由证明和必要验证支持。不得将缺少正式题解的题目标记为制作完成。

## 第四阶段：复核与交付

- 检查题面、解法、validator、checker、数据和题解之间的一致性。
- 汇总验证命令、结果、环境、失败修复和残余问题。
- 人工试做、独立审题和真实评测环境校准未执行时，明确列为待完成，不用 AI 自检冒充独立复核。
- 用 `python3 scripts/package_problem.py <题目目录>` 生成交付 ZIP，严格按白名单只包含题面（Markdown、Typst、PDF）、题解、标程、样例和输入答案数据；不包含 BRIEF、STATUS、报告、私有评测工具、字体或项目基础设施。检查记录保留在工作目录。
- CNOI 的全部样例须包含在交付包的 `down/` 中；可用 `--samples-only` 另外生成仅含下载样例的 ZIP。打包后核对输入答案成对完整，不能漏掉题面仅引用文件的大样例。
- 发布到外部平台另按用户授权执行；公开通用工具时采用独立文件清单与新的 Git 历史，不上传个人题目或凭据。

## 每题进度记录

在题目目录的 STATUS.md 中维护：

```markdown
# 题目进度

## 用户输入与决定
- 题目大意、预期解法、目标难度及已确认约束。
- 用户作出的继续、修改或放弃决定。

## 当前阶段
- 查重 / 解法审查 / 等待用户决定 / 制作 / 待复核 / 已交付。

## 产物与证据
- 文件路径、验证命令、结果和报告路径。

## 待办与局限
- 下一步、未验证事项、缺失信息；若 skill 暂不可用，记录恢复题解 skill 的待办。
```

修改题意、约束或算法后，更新受影响的报告与产物，并重新运行对应验证。新会话先读状态及证据，再决定需要补做什么。
